# Integrations

Every external dependency — SMS, payment gateway, media storage, cache — is behind a small interface selected by an environment variable, with a no-network default so the app runs anywhere. Nothing in the critical path depends on a service that blocks Iran; providers are domestic (Kavenegar, SMS.ir, Zarinpal, IDPay, Arvan) and the only foreign dependency is GitHub at development time.

Related: [architecture.md](architecture.md) · [deployment.md](deployment.md) · [operations.md](operations.md)

## SMS and OTP — `apps/accounts/sms.py`

### Contract

```python
class BaseBackend:
    name: str
    def send_otp(self, phone: str, code: str) -> bool: ...
    def send_sms(self, phone: str, text: str) -> bool: ...
```

Module-level `send_otp(phone, code)` and `send_sms(phone, text)` wrap `get_backend()` and **never raise**: exceptions are logged under `wonderkidz.sms` and `False` is returned, so a provider outage cannot break login or a moderation action. Callers that send notifications (moderation services, chat) additionally wrap the call in `try/except` and treat SMS as best-effort.

### Backends (`SMS_BACKEND`)

| Value | Class | OTP call | Notification call | Env vars |
|---|---|---|---|---|
| `console` (default) | `ConsoleBackend` | prints `[SMS/OTP] 09… -> کد تأیید وندرکیدز: 12345` to stdout and the log; stores the code in cache key `otp-last:{phone}` for tests | prints `[SMS] …` | — |
| `kavenegar` | `KavenegarBackend` | `POST https://api.kavenegar.com/v1/{key}/verify/lookup.json` with `receptor`, `token`, `template` | `POST …/sms/send.json` with `receptor`, `message` | `KAVENEGAR_API_KEY`, `KAVENEGAR_OTP_TEMPLATE` (default `wonderkidz-otp`) |
| `smsir` | `SmsIrBackend` | `POST https://api.sms.ir/v1/send/verify` with `mobile`, `templateId`, `parameters=[{name:"CODE", value}]`, header `x-api-key` | `POST …/send/bulk` with `messageText`, `mobiles` | `SMSIR_API_KEY`, `SMSIR_OTP_TEMPLATE_ID` |

Success is judged from the provider's JSON (`return.status == 200` for Kavenegar, `status == 1` for SMS.ir); HTTP errors raise inside the backend and are swallowed by the wrapper. Timeouts are 10 s.

**Template pre-approval.** Both providers require the OTP template to be registered and approved under the company's account before `verify/lookup` works; the planning docs budget days for this, so start it in week 1. The template must contain a `%token%` (Kavenegar) or `#CODE#` (SMS.ir) placeholder. Notifications use a plain sender line and need no template.

### OTP flow parameters (`config/settings.py`)

| Setting | Default | Meaning |
|---|---|---|
| `OTP_LENGTH` | 5 | digits generated by `OTPCode.generate` |
| `OTP_TTL_SECONDS` | 120 | code validity; the verify page shows a countdown of the same length |
| `OTP_RATE_LIMIT_PER_HOUR` | 5 | sends per phone per hour (cache-backed) |
| `OTP_DEV_CODE` | `""` | when set, this code always verifies — **development only**; `.env.example` sets `12345`, leave empty in production |

Per-message cost makes the rate limit a cost control as well as an abuse control.

### Where SMS is sent

| Event | Condition | Text |
|---|---|---|
| Login | always | OTP code via `send_otp` |
| Listing approved / rejected | `owner.notify_moderation` | see [moderation.md](moderation.md) |
| Listing taken down, user warned, user banned | always | see [moderation.md](moderation.md) |
| First buyer message in a conversation | `seller.notify_chat` | «وندرکیدز: پیام جدیدی دربارهٔ آگهی «…» دارید. <thread url>» |
| Saved-search matches | — | **not implemented** (flag exists on the user, no dispatcher) |

### Adding a backend

Subclass `BaseBackend` in `sms.py`, implement both methods returning `bool`, add it to the `BACKENDS` dict keyed by the value you want in `SMS_BACKEND`, read credentials from new settings in `config/settings.py` and document them in `.env.example`. Tests mock `requests.post` (see `tests/test_accounts.py`).

## Payments — `apps/payments/gateways.py`

### Contract

```python
class Gateway:
    name: str
    def start(self, payment, callback_url) -> str | None      # URL to redirect the user to, or None on failure
    def verify(self, payment, request) -> tuple[bool, str]    # (ok, ref_id)
```

`get_gateway()` returns the class registered for `PAYMENT_GATEWAY` (falls back to `FakeGateway`). Network errors return `None` / `(False, "")`; the views turn those into a FAILED payment and a friendly message («اتصال به درگاه پرداخت برقرار نشد…»).

### Flow

```
GET  /pay/plans/                    active Plans (+ ?listing=<code> to attach a listing)
POST /pay/start/<plan_id>/          creates Payment(pending, amount=plan.price, gateway=name)
                                    callback_url = SITE/pay/callback/?payment=<pk>
                                    gateway.start() → 302 to the gateway
…user pays…
GET|POST /pay/callback/             finds the Payment by ?payment= or by gateway authority/id
                                    gateway.verify() → PAID (ref_id, paid_at, plan applied) | FAILED | CANCELED
GET  /pay/<pk>/result/              outcome page
```

The callback is `csrf_exempt` (IDPay POSTs back) and idempotent: a payment that is no longer PENDING is not re-verified. Amounts are stored in **toman**; gateways receive rial (`× 10`).

### Gateways (`PAYMENT_GATEWAY`)

| Value | Class | Start | Verify | Env vars |
|---|---|---|---|---|
| `fake` (default) | `FakeGateway` | sets `authority = FAKE-…`, redirects to the in-app page `/pay/fake/<pk>/` with «پرداخت موفق» / «انصراف» buttons | `?status=ok` → paid with `ref_id = FAKE0000000N`; anything else fails; `status=cancel` → CANCELED | — |
| `zarinpal` | `ZarinpalGateway` | `POST {host}/pg/v4/payment/request.json` with `merchant_id`, `amount` (rial), `callback_url`, `description`, `metadata{mobile, order_id}`; accepts `code ∈ {100, 101}`; redirects to `{host}/pg/StartPay/{authority}` | requires `?Status=OK`; `POST …/verify.json` with `merchant_id`, `amount`, `authority`; ok on `code ∈ {100, 101}`, `ref_id` returned | `ZARINPAL_MERCHANT_ID`, `ZARINPAL_SANDBOX` (`true` → `sandbox.zarinpal.com`) |
| `idpay` | `IdpayGateway` | `POST https://api.idpay.ir/v1.1/payment` headers `X-API-KEY`, `X-SANDBOX`; body `order_id`, `amount` (rial), `phone`, `desc`, `callback`; stores `id`, redirects to `link` | reads `id` from POST/GET, `POST …/payment/verify` with `id`, `order_id`; ok on `status == 100`, `track_id` returned | `IDPAY_API_KEY`, `IDPAY_SANDBOX` |

### Plan effects (`apps/payments/views._apply_plan`)

| `Plan.kind` | Effect on PAID |
|---|---|
| `promote` | attached listing: `is_promoted = True`, `promoted_until = now + duration_days` (promoted listings sort first on home and search) |
| `subscription` | `user.listing_cap += 20` |
| `badge` | parent account → `account_type = pro` |

No fee is charged at launch: all seeded plans have `is_active = False`, and `/pay/plans/` shows «در حال حاضر هیچ هزینه‌ای برای فروشنده وجود ندارد». Switching a fee on is a data change in Django admin.

### Adding a gateway

Subclass `Gateway` with a unique `name`, implement `start` and `verify` with `requests` and a timeout, store the provider's transaction id on `payment.authority` inside `start`, and add the class to the `GATEWAYS` tuple. If the provider identifies the transaction with a parameter other than `Authority`/`id`/`authority`, extend the lookup in `views.callback`.

## Media storage

| Mode | Trigger | Behaviour |
|---|---|---|
| Local disk (default) | `S3_BUCKET` empty | `FileSystemStorage` under `MEDIA_ROOT` (`media/`); served by Django in `DEBUG`, must be served by the web server / CDN in production |
| S3-compatible (Arvan) | `S3_BUCKET` set | `storages.backends.s3.S3Storage` with `endpoint_url = S3_ENDPOINT` (default Arvan Tehran `https://s3.ir-thr-at1.arvanstorage.ir` in `.env.example`), `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_REGION` (default `ir-thr-at1`), public-read ACL, no query-string auth, no overwrite. `S3_PUBLIC_URL` (bucket or CDN hostname) becomes `MEDIA_URL`. |

Uploads are resized to WebP before storage ([architecture.md](architecture.md) → media pipeline), so the bucket only ever holds the two derived sizes.

## Cache and Redis

`REDIS_URL` set → `django.core.cache.backends.redis.RedisCache` (needs the `redis` package, which is in `requirements.txt`; the `core.E001` system check fails `migrate`/`check` if it is missing, because Django only imports it on the first cache call and that call is the OTP rate limit in the login view); otherwise `LocMemCache`. The cache holds OTP rate counters, the console backend's last code, and phone-reveal counters. Redis is recommended in production as soon as there is more than one worker (locmem counters are per process). django-rq / background jobs are **not** wired in v1; image processing is synchronous and expiry runs from cron ([operations.md](operations.md)).
